1. ERROS DE LÓGICA (confirmados executando o código)
----------------------------------------------------------------------
1.1 Estoque fica negativo
    Onde: services/caixa.py:15
    Causa: a checagem compara o estoque só com a quantidade do item atual,
    sem somar o que já está no carrinho. Com estoque = 1, bipar o mesmo
    produto 2 vezes passa nas duas checagens -> estoque final = -1.
    Solução: somar a quantidade já reservada antes de comparar:
        ja_no_carrinho = sum(qtd for prod, qtd in self.itens if prod.id == produto.id)
        if produto.estoque_atual < ja_no_carrinho + quantidade: raise ...

1.2 Quantidade zero ou negativa é aceita
    Onde: services/caixa.py:11
    Teste: adicionar_item("1", quantidade=-5) gerou total de R$ -50,00.
    Solução: validar no início -> if quantidade <= 0: raise ValueError(...)
    e reforçar no banco com CheckConstraint("quantidade > 0").

1.3 Programa quebra ao finalizar sem itens
    Onde: main.py:19
    Causa: digitar "f" logo de cara chama finalizar(), que lança
    ValueError("Venda vazia.") FORA do try -> traceback e o programa morre.
    Solução: tratar o erro ou só finalizar se houver itens.

1.4 Remover produto que já foi vendido estoura IntegrityError
    Onde: repositories/produto_repo.py:17
    Causa: ao deletar o Produto, o SQLAlchemy tenta colocar NULL em
    itens_venda.produto_id, que é NOT NULL. Teste confirmou o erro.
    Conceito: histórico de venda nunca deve ser apagado.
    Solução: "exclusão lógica" (soft delete): coluna ativo = Boolean e
    marcar ativo=False em vez de session.delete(). Também não use print()
    no repositório; retorne o valor ou lance exceção e deixe a interface
    decidir o que exibir.

1.5 Condição de corrida (race condition) no estoque
    Onde: repositories/produto_repo.py:12
    Causa: "ler estoque -> subtrair em Python -> gravar". Dois caixas
    vendendo o mesmo produto ao mesmo tempo podem sobrescrever um ao outro.
    Solução: deixar o banco fazer a operação de forma atômica:
        UPDATE produtos SET estoque_atual = estoque_atual - :qtd
        WHERE id = :id AND estoque_atual >= :qtd
    (ou SELECT ... FOR UPDATE com .with_for_update()). Se 0 linhas forem
    afetadas, falta estoque -> rollback.

1.6 Outros pontos de fluxo em main.py
    - forma_pagamento fixa em "dinheiro" (linha 19): pedir ao operador.
    - "F" maiúsculo não finaliza: use codigo.lower() == "f".
    - Ctrl+C / Ctrl+D (KeyboardInterrupt / EOFError) derrubam o programa
      sem mensagem.
    - Erros de banco (SQLAlchemyError) não são tratados.
    - Mesmo produto bipado várias vezes vira várias linhas de ItemVenda;
      agrupe por produto antes de gravar.


2. MODELAGEM DO BANCO (models/)
----------------------------------------------------------------------
2.1 Sem restrições de integridade (CheckConstraint) para preco >= 0,
    estoque_atual >= 0 e quantidade > 0. A validação deve existir no
    código E no banco (defesa em profundidade).
2.2 data_hora usa default=datetime.now (venda.py:10): hora do cliente e
    sem fuso. Prefira DateTime(timezone=True) com server_default=func.now().
2.3 forma_pagamento é texto livre: aceita "dinhero", "Pix", "pix".
    Use um Enum (Python enum.Enum + sqlalchemy.Enum).
2.4 declarative_base() e Column() são o estilo legado do SQLAlchemy 1.x.
    No 2.0 use class Base(DeclarativeBase) e Mapped[...]/mapped_column().
    Isso também resolve os erros do mypy "Class cannot subclass Base".
2.5 Código comentado de Categoria (produto.py:13-22) está errado se for
    reativado: a FK aponta para "categorias" mas a tabela se chama
    "categoria", e o relationship aponta para a própria classe. Corrija ou
    remova; código morto confunde.
2.6 Base.metadata.create_all() roda no import de main.py e não há Alembic
    configurado (falta alembic.ini/migrations), apesar de instalado.
    Rode "alembic init migrations" e gere as tabelas por migração.
